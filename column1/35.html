circuit breaker

design pattern, It protects a system. If a service fails, the circuit opens and temporarily stops requests to that service.

A circuit breaker stops repeated failing requests from overloading a system.

CQRS

It's a pattern. Command Query Responsibility Segregation

It separates operations that change data from operations that read data.

It can have different models and can be optimized independently

  • Two levels:
  • Simple CQRS — only classes/services are separated; there is a single database.
  • Full CQRS — separate databases, synchronization via events, eventual consistency.
Saga orchestration

It's a pattern. It's a way to manage a business transaction across multiple services

This is useful in microservice architectures, mostly for payments or order processing.

A central orchestrator coordinates the steps and handles failures or compensating actions.

Temporal

Temporal is a platform for orchestrating complex, long-running business processes. It manages workflow state and helps recover automatically from failures.

lazy loading

Lazy loading means related data is loaded only when it is accessed. It can avoid loading unnecessary data, but if used incorrectly, it can cause the N+1 query problem.

isolation levels

Isolation levels define how much one transaction is isolated from changes made by other transactions.

Common levels are Read Uncommitted, Read Committed, Repeatable Read and Serializable.

index

A data structure that helps the database find rows faster without scanning the whole table.

Can jump directly to the relevant locations instead of scanning every row. So fewer reads, faster lookups, especially on large tables.

slow database query

First, identify the exact query and check its execution plan with EXPLAIN or EXPLAIN ANALYZE. Then look at indexes, joins, filtering, sorting, and data volume. Make one change at a time, then measure again. Never guess or change multiple things blindly.

optimize a slow Doctrine query

I would first check, Symfony Profiler, Doctrine SQL Logger, Doctrine Doctor. Then the query plan, indexes. And if the data is massive, consider async processing, pagination.

DDD
  • Domain-Driven Design is a software development approach that focuses on business logic and business rules, rather than starting with databases, controllers, or frameworks.
  • DDD is especially useful for complex applications built with PHP, Symfony, Laravel, and microservices.
  • With DDD, these rules belong to the domain, not directly inside controllers.
  • DDD stands for Domain-Driven Design. It is an approach to designing software around business requirements and domain logic. The main concepts include Entities, Value Objects, Aggregates, Repositories, and Bounded Contexts. The goal is to keep business logic independent of frameworks, databases, and infrastructure, making complex systems easier to maintain and evolve.
  • Domain: The business area your application solves
  • Entity: An object with a unique identity, such as Order or Customer
  • Value Object: An immutable object defined by its values, such as Money or Email
  • Aggregate: A group of related domain objects with consistency rules
  • Aggregate Root: The main entity controlling access to an aggregate
  • Repository: An abstraction for retrieving and saving aggregates
  • Domain Service: Business logic that doesn't naturally belong to one entity
  • Bounded Context: A clearly defined boundary for a particular business model
  • Ubiquitous Language: Shared terminology used by developers and business experts

Kafka
  • Apache Kafka is a distributed event-streaming platform used to send, store, and process large volumes of events between services.
  • Kafka is commonly used in microservices, event-driven architecture, real-time analytics, and high-load systems.
  • One service publishes an event to Kafka, and other services consume that event asynchronously.
  • In PHP, a common Kafka client uses the php-rdkafka extension, which wraps librdkafka.
  • Apache Kafka is a distributed event-streaming platform used for asynchronous communication between services. Producers publish events to topics, and consumers read and process them. Kafka supports partitions for scalability, replication for fault tolerance, and message retention for replay. It is commonly used in microservices, real-time analytics, and high-load systems.
  • the most important concepts to understand are Producer, Consumer, Topic, Partition, Consumer Group, Offset, retry handling, and idempotency.
  • (Kafka = "This event happened.") Choose Kafka when:
  • Processing millions of events.
  • Building real-time analytics.
  • Sending events to multiple independent services.
  • Replaying historical events.
  • Streaming data into ClickHouse.
RabbitMQ
  • RabbitMQ is an open-source message broker that allows applications and microservices to communicate asynchronously using message queues.
  • RabbitMQ is commonly used for background jobs, notifications, order processing, microservices, and reliable task distribution.
  • A producer sends a message to RabbitMQ, and a consumer processes it asynchronously, without blocking the original request.
  • RabbitMQ and Kafka are similar, but they are not the same.
  • RabbitMQ is primarily a message broker for distributing and processing tasks.
  • Kafka is primarily an event-streaming platform for storing, distributing, and replaying events.
  • (RabbitMQ = "Please do this task.") Choose RabbitMQ when:
  • Sending emails asynchronously.
  • Processing background jobs.
  • Distributing tasks between workers.
  • Routing messages to different queues.
SQS
  • Amazon Simple Queue Service (SQS) is a fully managed message queue service from AWS used for asynchronous communication between applications and microservices.
  • SQS is similar to RabbitMQ in its primary use case: sending messages to queues and processing them using background workers.
  • The main difference is that AWS manages the queue infrastructure for you.
  • Unlike RabbitMQ's ACK mechanism, SQS consumers explicitly delete successfully processed messages.
  • If processing fails and the message is not deleted, it can become visible again after the visibility timeout.
  • Amazon SQS provides two main queue types (Standard Queue vs FIFO Queue)
background tasks in Symfony
  • Symfony Messenger supports Amazon SQS through its SQS transport.
  • In Symfony, I use Symfony Messenger for background tasks. It sends messages to a queue, such as RabbitMQ, Redis, Doctrine, or SQS, and workers process them asynchronously. For scheduled tasks, I can use Scheduler or cron. In production, workers can be managed with Supervisor or systemd, with retries, failure transport, and memory limits. This way, heavy tasks don't block the user's request.
